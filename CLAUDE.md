# CLAUDE.md

Undertow is a SwiftUI WireGuard client for macOS. It has an app target, a packet tunnel **system extension** built on vendored WireGuardKit (wireguard-go), and Swift Testing unit tests. See README.md for the user-facing overview.

Because it ships a Network Extension system extension, Undertow is distributed via Developer ID (notarized), not the Mac App Store — the App Store does not permit system extensions, and this packaging requires them.

## Build and test

```sh
# Build the app (also builds the Go bridge and the PacketTunnelSystemExtension target)
xcodebuild build -project undertow.xcodeproj -scheme undertow -destination 'platform=macOS' -derivedDataPath build

# Run the unit tests
xcodebuild test -project undertow.xcodeproj -scheme undertowTests -destination 'platform=macOS' -derivedDataPath build
```

- `-derivedDataPath build` keeps build output in the repo-local, gitignored `build/` directory instead of `~/Library/Developer/Xcode/DerivedData`; the built app ends up at `build/Build/Products/Debug/undertow.app`. Don't set a custom `SYMROOT` on the targets to achieve this instead — that flips the project into Xcode's "legacy build locations" mode, which is incompatible with Swift Package Manager and breaks package resolution entirely (this project depends on the local WireGuardKit package).

- Both the `undertow` and `undertowTests` schemes are shared files in `undertow.xcodeproj/xcshareddata/xcschemes/`. Xcode's autocreated schemes have been dropped more than once when targets were added, so keep these files and do not rely on autocreation.
- The app is single-instance on macOS: `SingleInstanceLock` holds a `flock` on `Application Support/Undertow/.instance.lock` in the container for the process lifetime, and `UndertowApp.init` exits a second copy after activating the first. If Run in Xcode appears to quit immediately, another copy is already running.
- The Go toolchain must be installed. `Vendor/wireguard-apple/build-bridge.sh` adds the common Go install paths to PATH and runs the WireGuardKitGo Makefile. It is invoked by the `WireGuardGoBridgemacOS` legacy target.
- Running `xcodebuild` inside the Claude Code sandbox fails during package resolution (`permissionDenied`) and can leave a stray `27.0-27A266a/` cache directory in the repo root. Don't commit that directory. Run builds outside the sandbox when needed.

## Architecture

- `TunnelManager` (`undertow/Services/TunnelManager.swift`) is the single `@Observable` source of truth. Views read it through `@Environment(TunnelManager.self)`. It owns the tunnel list, statuses, statistics, and throughput histories, and it polls the backend once a second.
- `TunnelBackend` is the protocol for the connection engine. It has two implementations:
  - `NetworkExtensionTunnelBackend`: one `NETunnelProviderManager` per tunnel, matched to it by the `tunnelID` key in `providerConfiguration`.
  - `SimulatedTunnelBackend`: in-memory, with fake traffic. Used by previews, tests, and builds without the extension or entitlement. It keeps no state across launches, so `isSynchronized` is false at launch and `TunnelManager.start()` re-synchronizes every tunnel into it.
- `TunnelBackendKind.automatic` uses the NE backend only when `isExtensionBundled && hasPacketTunnelEntitlement` is true.
- `Tunnel` is a plain persistable record. Live state is stored in `TunnelManager` dictionaries keyed by `Tunnel.id` and never on the model itself.
- Persistence is `TunnelPersistence`, which writes JSON to Application Support. The file contains private keys, so keep the `.atomic, .completeFileProtection` write options. Tests and previews use `TunnelPersistence.ephemeral()`.

### App ↔ extension contract

- The packet tunnel provider is a **Network Extension system extension** (`PacketTunnelSystemExtension` target, product type `com.apple.product-type.system-extension`, packaged into `Contents/Library/SystemExtensions/` — not an app extension in `PlugIns/`). It was migrated from an app extension; see "System extension packaging" below for what that changes.
- `undertow/Services/TunnelProviderMessage.swift` compiles into **both** the app and the `PacketTunnelSystemExtension` target, through a membership exception in the synchronized folder group in `project.pbxproj`. Keep it dependency-free (Foundation only), and change both sides together.
- The app stores the wg-quick text (from `WireGuardConfigFile.serialize`) in the data-protection keychain via `TunnelConfigurationKeychain` (also compiled into both targets) and puts only a persistent keychain reference in `NETunnelProviderProtocol.passwordReference`, plus `ConfigurationKey.tunnelID` and a SHA-256 `configurationDigest` in `providerConfiguration`. The extension loads the text with `TunnelConfigurationKeychain.load(reference:)` and parses it with `PacketTunnelSystemExtension/WgQuickConfigParser.swift`. Both targets declare the same `keychain-access-groups` entitlement (`$(AppIdentifierPrefix)io.craterlabs.undertow`); never put configuration text in `providerConfiguration`, it is readable in plaintext with `scutil --nc show`.
- `TunnelBackend.isSynchronized(_:)` compares the digest, name, and on-demand flag; `TunnelManager.start()` re-synchronizes any tunnel that is out of date, which is also how storage migrations roll out.
- **There are two wg-quick parsers.** `WireGuardConfigFile` in the app is strict, gives line-numbered errors, and produces the app's own model types. `WgQuickConfigParser` in the extension is lenient and produces WireGuardKit types. If you add support for a config key, update both, plus `serialize`.
- The `PacketTunnelSystemExtension` extension is sandboxed and needs `com.apple.security.network.client` and `com.apple.security.network.server` in addition to the packet-tunnel entitlement; without them wireguard-go cannot open UDP sockets and DNS resolution in the extension fails with "Operation not permitted".
- Diagnose extension failures with a live capture, not `log show` (which returns nothing on this machine): `log stream --info --predicate 'process == "PacketTunnelSystemExtension"'`. The adapter error "WireGuardAdapterError error 0" is `cannotLocateTunnelFileDescriptor`; see the vendored adapter patch in `Vendor/wireguard-apple/VENDOR.md` (this patch is extension-packaging-agnostic — it's pure syscalls / `NEPacketFlow` KVC, unaffected by the app-extension-to-system-extension move).
- The provider bundle ID is always `Bundle.main.bundleIdentifier + ".PacketTunnel"` (`io.craterlabs.undertow.PacketTunnel`). For a system extension, Apple requires the bundle's **filename** to equal that identifier exactly (`io.craterlabs.undertow.PacketTunnel.systemextension`), so `PacketTunnelSystemExtension`'s `PRODUCT_NAME` and `PRODUCT_BUNDLE_IDENTIFIER` are both pinned to that string — don't let Xcode regenerate them from the target name.

### System extension packaging

- Activation goes through `SystemExtensions.framework`, not just `NETunnelProviderManager`: `SystemExtensionActivator` (`undertow/Services/SystemExtensionActivator.swift`) submits an `OSSystemExtensionRequest` from `NetworkExtensionTunnelBackend.prepare()`, fire-and-forget. Activation can require the person to approve the extension in System Settings → Privacy & Security, which may take an arbitrary amount of time (or never happen), so nothing blocks on it — `NETunnelProviderManager` configs are loaded/saved independently and just stay inert (tunnels fail to start) until the extension is actually active. Current state is published through `SystemExtensionActivationStatus.shared` and shown in `SettingsView`.
- The app needs the `com.apple.developer.system-extension.install` entitlement to submit activation requests at all; both the app and `PacketTunnelSystemExtension` declare `com.apple.developer.networking.networkextension`. **The value differs by configuration**, because Apple's profiles differ: Mac *Development* profiles only ever grant `packet-tunnel-provider`, while Developer ID ("Direct") profiles only grant `packet-tunnel-provider-systemextension`. So Debug uses `undertow/undertow-Debug.entitlements` and `PacketTunnelSystemExtension/PacketTunnelSystemExtension-Debug.entitlements` (plain value), and Release uses `undertow.entitlements` / `PacketTunnelSystemExtension.entitlements` (`-systemextension` value). Keep each pair otherwise identical. Toggling capabilities or regenerating profiles cannot fix a mismatch here; check the profile's actual entitlements with `security cms -D -i <profile>`.
- **Release signing is manual Developer ID**, because automatic signing always signs for development first and so can't carry the `-systemextension` value: `CODE_SIGN_IDENTITY = "Developer ID Application"`, with the manually created portal profiles `Undertow Developer ID` (app) and `Undertow PacketTunnel Developer ID` (extension) as `PROVISIONING_PROFILE_SPECIFIER`. Xcode-managed "Team Direct" profiles can't be used with manual signing. `xcodebuild ... -allowProvisioningUpdates` downloads the manual profiles if they're missing locally. Debug stays automatic development signing. A Release build still needs notarization before anyone else can run it.
- Xcode's `AddEntitlement`-style tooling may refuse to write `com.apple.developer.networking.networkextension` on a system-extension product type or the `-systemextension` value, reporting it "unavailable for this target" — that's a gap in the tool's capability table, not an Apple restriction (TN3134 and Apple's System Extensions docs confirm this value and product type). Edit the `.entitlements` plist directly in that case.
- No current MCP/Xcode tooling can delete a target object, add an existing file's membership to a second target, or add a package-product dependency. Editing `project.pbxproj` directly works for all three (that's how the old `PacketTunnel` app-extension target was removed and WireGuardKit linked to `PacketTunnelSystemExtension`); validate with `plutil -lint` and a build afterwards.
- **Connect on Demand has no "paused" state.** `NEOnDemandRuleConnect` (`interfaceTypeMatch = .any`) reconnects the tunnel almost immediately while the Mac is online — confirmed live that even just *saving* `isOnDemandEnabled = true` on an `NETunnelProviderManager` is by itself enough to trigger a reconnect, not only Apple's documented "any app opens a connection" trigger. Two earlier attempts at a fix got this wrong: (1) leaving on-demand disabled at the system level after a manual stop until the next explicit `start(_:)`, which silently broke on-demand for however long the tunnel stayed disconnected while the UI still showed it as "on"; (2) auto-restoring on-demand a few seconds after a stop, which — per the finding above — just reconnects the tunnel a few seconds later, reproducing the original "disconnect doesn't stick" complaint with a delay. **The actual fix**: `TunnelManager.disconnect(_:)` turns the tunnel's `connectOnDemand` *preference* off (persisted, via `update(_:)`, so the on-demand toggle reflects it honestly) before calling `backend.stop(_:)`, whenever it was on. `NetworkExtensionTunnelBackend.start(_:)`/`stop(_:)` are back to plain one-liners with no on-demand logic of their own — that responsibility lives in `TunnelManager`, where the persisted preference actually is. Reconnecting or turning the toggle back on are both one click away; there's no hidden timer. Verified live via a disposable `TunnelManager`+`NetworkExtensionTunnelBackend` pair exercising the real `disconnect(_:)` method: `connectOnDemand` flips to `false` (in memory, on disk, and in the live system config) and `scutil --nc status` stays Disconnected for a full 20s with zero reconnects.

### Type name collisions

The app defines its own `TunnelConfiguration`, `PeerConfiguration`, `InterfaceConfiguration`, `IPAddressRange`, and `Endpoint` (`undertow/Models/WireGuardConfiguration.swift`). WireGuardKit uses the same names. The app target must **not** import WireGuardKit. Only `PacketTunnelSystemExtension/` does.

## Conventions

- Swift settings: `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` and approachable concurrency. Model, value, and parsing types are explicitly marked `nonisolated` (for example `nonisolated struct Tunnel`). Follow that pattern for new non-UI types so they stay usable from tests and background contexts.
- Error enums conform to `LocalizedError` and use full-sentence, user-facing `errorDescription`s with curly quotes (“ ”). Operation failures (connect, disconnect, install, import, persistence, configuration validation) never show as an in-app alert; they go through `ErrorNotifier.post(title:message:)`, which delivers a macOS notification instead. `TunnelManager.report(_:title:)` is the main caller; call `ErrorNotifier.post` directly for UI-layer failures that don’t go through `TunnelManager` (see `ContentView` and `TunnelEditorView`). `TunnelManager.poll()` also posts one for a tunnel stuck past `handshakeGracePeriod` with no handshake, edge-triggered via `handshakeWarningsSent` so it fires once per stall rather than every polling tick; the DNS-unreachable warning stayed an inline banner in `TunnelEditorView`/`TunnelDetailView` since it's persistent contextual state the person is actively looking at, not a one-shot failure.
- `ErrorNotifier.installDelegate()` must run from `UndertowApp.init()` (before the app finishes launching, per Apple’s requirement for `UNUserNotificationCenterDelegate`); `requestAuthorizationIfNeeded()` can run later, from a scene’s `.task`. Both no-op under Xcode Previews and the hosted test runner.
- Interface or tunnel names: at most 15 characters, from `[A-Za-z0-9_=+.-]`. Use `Tunnel.validateName` and `Tunnel.sanitizedName(from:)`.
- Platform-specific code is guarded with `#if os(macOS)`. The menu bar extra and Settings scene are macOS-only.
- Doc comments (`///`) on types and on non-obvious members. Use `// MARK: -` to section longer files.
- Tests use Swift Testing (`@Suite`, `@Test`, `#expect`), not XCTest. Generate keys with `WireGuardKey.generatePrivateKey()` instead of hardcoding them.
- Previews seed data with `Tunnel.sampleTunnels()` and `TunnelManager.seedForPreview(_:)` (`undertow/Services/PreviewData.swift`).
